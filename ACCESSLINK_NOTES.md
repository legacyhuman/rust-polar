# Polar AccessLink documentation notes

Checked on 2026-10-21 against the official [AccessLink documentation](https://www.polar.com/accesslink-api/) and [Swagger](https://www.polar.com/accesslink-api/swagger.yaml), using text fetches only.

The HTML documentation includes current non-transactional resources for daily activity, continuous heart rate, sleep, Nightly Recharge, SleepWise, cardio load, physical info, and exercises. The published Swagger currently declares only a small subset of those paths (notably exercises, user registration/profile, physical info, notifications, plus legacy transactional endpoints). Therefore, absence from Swagger is not evidence that a documented endpoint is unavailable. Implementations should avoid legacy transactional APIs and use the current HTML operation descriptions for paths missing from Swagger; keep this discrepancy visible when verifying later.

Confirmed schema details that affect decoding:

- Daily activity list is a JSON array. Summary keys include `start_time`, `end_time`, `active_duration`, `inactive_duration`, `daily_activity`, `calories`, `active_calories`, `steps`, `inactivity_alert_count`, `distance_from_steps`; optional `samples` contains `date`, nested step samples, activity-zone samples, and inactivity stamps. The date/sample timestamps do not establish a UTC offset.
- Exercise identifiers are hashed strings in documented examples. Top-level fields use underscores such as `upload_time`, `start_time_utc_offset`, `heart_rate`, `training_load`, and `heart_rate_zones`; sample subfields use hyphens. `samples[].data` is documented as a comma-separated string, not an array of timestamp/value objects. The original archived response remains authoritative for wire fidelity.
- Continuous heart rate returns a date with `heart_rate_samples` containing `heart_rate` and `sample_time`; the sample time is a clock value such as `00:02:08`, without an explicit timezone.
- Cardio load returns one object per day, including days where `cardio_load_status` is `LOAD_STATUS_NOT_AVAILABLE`; zero numeric values and unavailable status must both be retained.
- Cardio Load has separate documented routes for the date range (`/v3/users/cardio-load/date?from=…&to=…`), day (`/v3/users/cardio-load/{date}`), and period history (`/v3/users/cardio-load/period/days/{days}` and `/period/months/{months}`). `/users/cardio-load/history?from=…&to=…` is not a documented route; using it returns `Invalid date history for date` even when the dates are valid.
- Exercise detail is documented at `/v3/exercises/{exerciseId}`. A live comparison of 23 Polar Loop exercises found no fields unique to detail; it omitted samples and heart-rate zones for all 23, and route for the 4 exercises where the list included one. Keep the request builder and replay support, but do not spend a request on every routine sync unless Polar changes the response.
- Sleep list responses use the `{ "nights": [...] }` wrapper and snake_case names. `hypnogram` and `heart_rate_samples` are JSON objects keyed by sample time, not arrays. Nightly Recharge uses `{ "recharges": [...] }`; `hrv_samples` and `breathing_samples` are likewise keyed maps. Their sample times remain provider-local.
- SleepWise alertness and circadian-bedtime responses are arrays with snake_case names. Alertness includes `grade`, `grade_classification`, `validity`, `result_type`, and `hourly_data`; circadian bedtime includes preferred-sleep and sleep-gate period timestamps, `quality`, and `sleep_timezone_offset_minutes`. Preserve these local-looking timestamps and the explicit offset as separate source fields.

The documentation also lists Elixir biosensing endpoints, but the API output is device- and permission-dependent. Do not infer those measurements are available from Polar Loop; only request and record them if the actual documented support and user account permit it.
